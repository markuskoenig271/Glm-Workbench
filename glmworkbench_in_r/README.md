# glmworkbenchR — GLM Workbench as an R Shiny package

The R port of the Python GLM Workbench, built as a **[golem](https://thinkr-open.github.io/golem/)
application** — the "Shiny app as an R package" standard: `DESCRIPTION`
declares the dependencies, roxygen generates `NAMESPACE` and `man/`, every
screen is a namespaced module (`NS()` + `moduleServer()`, one `mod_*.R` per
screen), the data layer lives in `fct_*.R`, configuration in
`inst/golem-config.yml`, the development workflow in `dev/`, and
**`run_app()` is the single entry point** for RStudio, the command line, the
EUC launchers and the Electron desktop shell. The folder is named
`glmworkbench_in_r/` on purpose: everything above and next to it is the
Python app.

**Feasibility scope:** Data Import (built-in registry datasets + CSV upload
with column mapping, kind-aware validation report) and Feature Engineering /
cleansing (cap, quantile/uniform binning, log transform). The modelling
screens (02, 04–07) are namespaced placeholders so the page structure matches
the real app 1:1.

```
│   ├── run_app.R                  # run_app(..., data_dir) via golem::with_golem_options — exported
│   ├── app_config.R               # app_sys(), get_golem_config()
│   ├── app_ui.R / app_server.R    # navbar UI (+ golem_add_external_resources) / module wiring

│   ├── fct_preprocessing.R        # cap_column, bin_numeric, log_transform

```

The data loaders read the same `data/raw/freMTPL2*.parquet` files the Python
app uses (via the dependency-free `nanoparquet` package), including the
severity inner join onto the frequency rating factors. `data_dir()` resolves
the folder in this order: the golem option set by `run_app(data_dir = …)` →
`GLM_WORKBENCH_DATA_DIR` env var → `data_dir` in `inst/golem-config.yml` for
the active environment (`GOLEM_CONFIG_ACTIVE`) → the package's own
`inst/extdata` (empty by default) → `../data/raw` relative to the working
directory (i.e. the Python repo layout when the `.Rproj` is open).

`R/` is written in **tidyverse style**: the native `|>` pipe, dplyr verbs
(`mutate`, `select`, `inner_join`, `slice_head`, dynamic column names via
`"{col}_band" :=`), tidyr (`pivot_longer` in the validation report), purrr,
tibbles, and `readr` for CSV upload — the direct R analogue of the pandas code
in `pricing_engine/`. Package hygiene: no `library()`/`source()`, columns are
referenced through `.data[[col]]` / `all_of()` so `R CMD check` finds no
undefined globals.

## Development in RStudio

### Prerequisites

- **R ≥ 4.1** (the code uses the native `|>` pipe; developed on R 4.2.1) and
  **RStudio** (any recent version). **Rtools is NOT needed** — the package
  and all its dependencies are pure R / CRAN binaries.
- The freMTPL2 parquet files in the Python repo's `data/raw/` (gitignored).
  If they are missing, download them once from the repo root:

  ```
  curl -sL -o data/raw/freMTPL2freq.parquet https://data.openml.org/datasets/0004/41214/dataset_41214.pq
  curl -sL -o data/raw/freMTPL2sev.parquet  https://data.openml.org/datasets/0004/41215/dataset_41215.pq
  ```

  (same files the Python app uses; `data_dir()` finds them automatically at
  `../data/raw` when the `.Rproj` is open, i.e. the working directory is
  this folder.)

### First time: build and run the app

1. Clone the repo and open **`glmworkbench_in_r/glmworkbenchR.Rproj`** in
   RStudio (File ▸ Open Project). The working directory is now the package
   root; the Build pane appears because the `.Rproj` is configured as a
   package project (`BuildType: Package`, roxygen on install).
2. Install the development tooling and every dependency declared in
   `DESCRIPTION` (Imports + Suggests — includes shiny, bslib, golem, config,
   nanoparquet, the tidyverse pieces, testthat …):

   ```r
   install.packages("devtools", type = "binary")
   devtools::install_deps(dependencies = TRUE, upgrade = "never")
   ```

   `type = "binary"` / `upgrade = "never"` keep the CRAN binaries that match
   your R version. On an older R (e.g. 4.2.x, whose CRAN binaries are frozen)
   a plain `install.packages()` asks *"Möchten Sie versuchen, die Pakete,
   welche eine Kompilierung erfordern, aus den Quelltexten zu
   installieren?"* — answer **Nein**: the already-installed binary versions
   are the ones the package was verified with, and compiling newer sources
   with Rtools is slow and can leave mismatched packages behind.

3. Load the package into the session and start the app:

   ```r
   devtools::load_all()   # Ctrl+Shift+L — sources R/ into the session, no install needed
   run_app()              # opens the app in the RStudio viewer / browser; blocks the console
   ```

   Stop the app with the red stop button or **Esc** in the console.
   `run_app(options = list(launch.browser = TRUE))` forces the system browser.
   Note: RStudio's **"Run App" button does not apply** — there is no
   `app.R`; a golem app is always started through `run_app()`.

4. (Optional) Install it into your user library so it also runs outside
   RStudio: **Build ▸ Install** (Ctrl+Shift+B, runs roxygen first), then
   `Rscript -e "print(glmworkbenchR::run_app())"` works from anywhere, and the
   `.bat` launchers / the Electron exe pick the installed version up.

### The everyday loop

The golem way is `dev/run_dev.R` (source it, or run it line by line):

```r
golem::document_and_reload()   # roxygen (NAMESPACE + man/) + load_all() in one go
run_app()                      # starts the app
```

…or the plain devtools equivalents / RStudio Build pane:

```r
devtools::load_all()      # Ctrl+Shift+L — sources R/ into the session, no install needed
devtools::document()      # Ctrl+Shift+D — roxygen → NAMESPACE + man/ (after editing #' headers
                          #   or adding @export / @importFrom)
devtools::test()          # Ctrl+Shift+T / Build ▸ Test Package — testthat (54 tests);
                          #   the real-data tests skip when ../data/raw is not there
devtools::check()         # Ctrl+Shift+E / Build ▸ Check Package — R CMD check (build + tests +
                          #   docs + code checks); expected: 0 errors, 0 warnings, at most the
                          #   harmless "unable to verify current time" NOTE. check() runs the
                          #   tests in a temp copy, so set
                          #   Sys.setenv(GLM_WORKBENCH_DATA_DIR = "C:/path/to/repo/data/raw")
                          #   first if you want the real-data tests to run inside check too
devtools::install()       # Ctrl+Shift+B / Build ▸ Install — installs into your user library
devtools::build()         # Build ▸ Build Source Package — glmworkbenchR_0.1.0.tar.gz for handing over
```

Troubleshooting: *"Data file not found: …/data/raw/freMTPL2freq.parquet"* —
the working directory is not the package root or the parquet files are
missing (see Prerequisites); pass `run_app(data_dir = "C:/…/data/raw")` or set
`GLM_WORKBENCH_DATA_DIR`. *"Port … already in use"* — an earlier app is still
running; stop it, or leave `port` unset (Shiny then picks a free random
port) / pass `options = list(port = httpuv::randomPort())`.
Stale state after editing package code — `golem::detach_all_attached()` then
`golem::document_and_reload()` (that is what `dev/run_dev.R` does).

Shiny run options go through `run_app(options = list(port = 8613,
launch.browser = FALSE))`; app options through the golem opts
(`run_app(data_dir = "…")`, readable inside the app with
`golem::get_golem_options("data_dir")`). Environment-specific settings live
in `inst/golem-config.yml` (`get_golem_config("data_dir")`), selected with
`GOLEM_CONFIG_ACTIVE=production|dev`.

Conventions when extending the app (`dev/02_dev.R` has these as ready-made
lines): turn a placeholder into a real screen with
`golem::add_module("frequency_model", with_test = TRUE)` → fill
`R/mod_frequency_model.R` (`mod_frequency_model_ui(id)` /
`mod_frequency_model_server(id, state)`), wire it in `app_ui.R` /
`app_server.R`; engine logic goes into `golem::add_fct("glm")` →
`R/fct_glm.R` with roxygen headers (`@export` if user-facing); a new CRAN
dependency is added with `usethis::use_package("<pkg>")` (edits
`DESCRIPTION`) plus an `@importFrom` line in `R/glmworkbenchR-package.R` or
`pkg::fun()` calls — and to the `REQUIRED_PACKAGES` list in
`desktop/main.js` so the exe auto-installs it; static assets via
`golem::add_css_file()` / `add_js_file()` into `inst/app/www`; then
`document()` → `test()` → `check()`.

## Running it without RStudio

Requirements: **R only — RStudio is NOT needed** (RStudio is just an IDE; the
Shiny runtime ships with the `shiny` package and serves the app to any
browser). One-time package install:

```
Rscript -e "install.packages(c('shiny','bslib','DT','nanoparquet','dplyr','tidyr','purrr','readr','tibble','rlang','tidyselect','golem','config','pkgload'), repos='https://packagemanager.posit.co/cran/2026-09-01')"
```

(The repo URL is a **dated Posit Package Manager snapshot** — the same one the
Electron exe pins (see below) — so manual installs get the same package
versions as the exe's auto-setup. Plain `https://cloud.r-project.org` works
too if you just want latest CRAN.)

Then double-click one of the launchers (both find the installed R via the
registry, with a Program Files fallback; both use the installed
`glmworkbenchR` if present and otherwise `pkgload::load_all()` this source
folder, so they work with or without a prior `devtools::install()`):

- **`run_app.bat`** — opens the app as a tab in the default browser. Stop it
  with Ctrl+C in the console window (or close the console).
- **`run_app_desktop.bat`** — starts the server headless on port 8613 and
  opens it in Edge/Chrome **app mode** (`--app=URL`): an own window without
  tabs or address bar, so it looks and feels like a native desktop
  application. **Closing that window shuts the R server down again** (the
  launcher waits on the window, then kills whatever process is listening on
  the port). Uses a dedicated browser profile in `%TEMP%` so it works even
  when a normal Edge/Chrome session is already open.

Or from the command line with the package installed:

```
Rscript -e "print(glmworkbenchR::run_app())"
Rscript -e "print(glmworkbenchR::run_app(data_dir = 'C:/path/to/data/raw', options = list(port = 8613, launch.browser = FALSE)))"
```

(`run_app()` returns the Shiny app object — golem style — and printing it
runs it; the `print()` makes that explicit for `Rscript -e`.)

## EUC deployment findings ("can we ship an executable?")

There is **no true compiled .exe** for R/Shiny — R is an interpreted runtime,
like Python. What exists, in increasing order of packaging effort:

1. **Installed R + launcher script** (what `run_app.bat` does). Users need R
   installed once (plain R, no RStudio, no admin-share issues if IT deploys
   it); the app itself is just a folder — or, now that it is a package, a
   `glmworkbenchR_0.1.0.tar.gz` built with `devtools::build()` that IT can
   install with `install.packages("glmworkbenchR_0.1.0.tar.gz", repos = NULL)`.
2. **R-Portable bundled with the app** — a zero-install folder on a network
   share or USB: copy `R-Portable/` next to the app, point the launcher's
   `RSCRIPT` at it. Nothing to install on the user's machine at all.
3. **Electron wrapper** — implemented in `desktop/`. A Node/Electron shell
   that finds R (bundled `r-portable/` in resources → `r-portable/` next to
   the portable .exe → `GLM_WORKBENCH_RSCRIPT` env var → registry → Program
   Files), spawns `glmworkbenchR::run_app()` on a random free port (parsed
   from Shiny's "Listening on" line), shows the app in its own native window
   with taskbar identity, and taskkills the R process tree on close.
   **End-user contract: install R once — everything else is managed by the
   exe.** On every start the shell checks the CRAN packages the app needs
   AND that the bundled `glmworkbenchR` version is installed; anything
   missing is installed automatically into the user's R library (CRAN
   binaries for the dependencies, the bundled package source for
   `glmworkbenchR` itself — pure R, so no Rtools needed; first-run setup
   window with live progress log; resumes if interrupted; re-runs when the
   exe ships a new package version). **Package versions are pinned:** the
   auto-install pulls from a dated Posit Package Manager snapshot
   (`CRAN_SNAPSHOT` in `main.js`, overridable per machine with the
   `GLM_WORKBENCH_CRAN` env var for proxies/internal mirrors), so every
   user gets identical versions no matter when they first run the exe;
   bump the snapshot date deliberately with a re-test. If R itself is missing, a self-help
   page with copy-pasteable instructions is shown instead of the app. The
   freMTPL2 parquet files are bundled (`GLM_WORKBENCH_DATA_DIR` points at
   them), so the built-in datasets work on target machines. Dev run:
   `npm install` then `npm start` inside `desktop/`. Distributables:
   `npm run dist` → `desktop/dist/` with a **portable single-file .exe**
   and an **NSIS Setup.exe installer**. Heavyweight (hundreds of MB with
   Chromium) and needs Node.js to build. Caveat: auto-install uses CRAN
   binaries; on outdated R versions some packages may only exist as source
   (needs Rtools) — the failure page then advises installing a current R.
   Build gotcha: without Windows Developer Mode, electron-builder's
   winCodeSign cache fails to extract (macOS symlinks); fix by extracting
   `winCodeSign-2.6.0.7z` manually with 7za into
   `%LOCALAPPDATA%\electron-builder\Cache\winCodeSign\winCodeSign-2.6.0`
   and ignoring the two darwin symlink errors.
4. **RInno** — generates an Inno Setup Windows installer that bundles
   R-Portable + the app + a desktop shortcut. Historically the standard
   answer, but the package is no longer actively maintained; treat as legacy.
5. **shinylive / webR (WASM)** — exports the app to static files that run
   **entirely in the browser with no R installed anywhere**. Genuinely
   zero-install, but package support is limited to WASM builds and there is
   no local file-system/SQLite access — good for demos, not for a workbench
   that reads local parquet and writes a local DB.

Recommended for a real EUC rollout: **option 2** (R-Portable + launcher) for
zero-install, or option 1 if a managed R install is acceptable.

**Version pinning (decided 2026-09-02):** the exe pins its installs to a
dated Posit Package Manager snapshot instead of using `renv`. Rationale:
`renv::restore()` of older versions often has no CRAN binaries left and
falls back to source compilation — that would break the "R + CRAN access,
nothing more" end-user contract (no Rtools). A dated P3M snapshot gives the
same determinism as a lockfile, served as binaries for current R versions,
and the user never sees it. `renv` remains a dev-machine option only.

## Deliberate parallels to the Streamlit app

| Streamlit | Shiny equivalent here |
| --- | --- |
| `st.session_state["portfolio"]/["spec"]` | `reactiveValues` state passed to every module |
| one file per page in `pages/` | one module file `R/mod_*.R` per page |
| `pricing_engine.data` registry/loaders | `R/fct_datasets.R` |
| `pricing_engine.preprocessing` | `R/fct_preprocessing.R` |
| `pyproject.toml` + `uv sync` | `DESCRIPTION` + `devtools::install_deps()` |
| `uv run pytest` | `devtools::test()` |
| `ruff` / `mypy` | `devtools::check()` |
| single active model slot + kind gate | `state$model` / `state$model_meta` (reserved) |

One behavioural difference to note for the study: browser refresh starts a
new Shiny session (dataset must be reloaded) — same as Streamlit.
